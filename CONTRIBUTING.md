# Contributing

Assay 0.15 is a thin stitching layer. Object behaviour lives in two sibling
products, so the first question about any change is which repository owns it:

- [`absorb-anything`](https://github.com/NB-Corp/absorb-anything) — envelope,
  manifest, layout, managed receipt, Templates, update planning, and the
  Source / Analysis / Knowledge objects, plus the `absorb` CLI.
- [`own-work`](https://github.com/NB-Corp/own-work) — Task, Roadmap, Spec,
  System, plus the `ownwork` CLI.
- this repository — the suite lifecycle (`init`, `check`, `status`, `prime`,
  `explain`), the merged object table, and the mount that puts both halves under
  the `assay` binary.

A change to how an object behaves belongs upstream, not here. Changes here
should be about stitching: what the suite owns, what it mounts, and what the
merged surface says.

## Repository map

```text
packages/assay/               the assay package: lifecycle, semantics, mount, CLI
skills/assay-builder/         agent-facing Skill that calls this repo's CLI
examples/framework-template/  sanitized generated workspace
docs/                         command docs, workspace docs, background, and decisions
scripts/                      validation, smoke, and install helpers
```

## Local development

Use Node.js >=22.13.0 and the repository-pinned pnpm 11.3.0. Older Node
versions are outside the supported install and CLI runtime contract.

The three repositories are checked out side by side, and `pnpm-workspace.yaml`
overrides resolve the halves from those checkouts. Build them first:

```bash
cd ../absorb-anything && pnpm install && pnpm build
cd ../own-work        && pnpm install && pnpm build
cd ../assay
```

Then, in this repository:

```bash
pnpm install
pnpm build
pnpm typecheck
pnpm lint
pnpm test
pnpm smoke
```

Run the full repository check before committing:

```bash
./scripts/check.sh
```

On Windows PowerShell:

```powershell
.\scripts\check.ps1
```

The full check runs build, typecheck, lint, tests, the CLI smoke flow (which
includes the committed public example), and the publish-shape check.

### Tests must not touch the user's home directory

Tests spawn the built CLIs and create real workspaces, so every suite pins the
clone registry (`ABSORB_CLONE_REGISTRY`) at a disposable path and pins Git's
`core.autocrlf=false` through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/
`GIT_CONFIG_VALUE_0`. See `packages/assay/vitest.config.ts`. A test that reads or
writes the real home directory is a defect regardless of whether it passes.

## Public example

`examples/framework-template/` is a sanitized workspace generated by the 0.14
CLI. It stays committed as the cheapest regression proof that the thin layer
still reads a workspace the monolith wrote; the smoke script validates it with:

```bash
node packages/assay/dist/cli.js check --root examples/framework-template
node packages/assay/dist/cli.js update --root examples/framework-template --dry-run
```

Do not regenerate it casually. Its value is precisely that 0.14 produced it.

## Public boundary

Do not commit:

- real external-system snapshots, private references, customer or project data, generated releases, or runtime logs;
- `.env` files, API keys, tokens, credentials, or local absolute paths;
- one-off delivery reports, temporary validation output, caches, or compiled artifacts;
- runtime contents under `.assay/backups/`, `.assay/events/`, or `.assay/.runtime/`.

Use sanitized examples when a workflow needs demonstration data. Public docs should explain product behavior and reader actions, not private context, temporary acceptance criteria, or implementation diary notes.
